# همکاری با Skillها و اسناد پروژه

## ترتیب مرجع‌ها

هنگام کار در پروژه واقعی، قبل از بازنویسی متن این ترتیب را رعایت کن:

1. فایل‌های Source of Truth و تصمیم‌های Locked
2. قوانین برند و لحن
3. رفتار واقعی محصول و کد
4. درخواست همین Task
5. Skillهای عمومی طراحی، UX Writing، RTL و QA
6. این Skill برای تبدیل متن به زبان انسانی

اگر دو مرجع تعارض دارند، مورد را Flag کن. تصمیم استراتژیک جدید اختراع نکن.

## همکاری با Skill طراحی

وقتی همراه Skillهای طراحی مثل `design-taste-frontend` یا `redesign-existing-projects` استفاده می‌شود:

- این Skill مسئول وضوح و زبان مخاطب است.
- Skill طراحی مسئول Hierarchy، Layout، typography، spacing و interaction است.
- هیچ‌کدام نباید وعده محصول یا مسیر تجاری جدید بسازند.
- متن را برای جاگرفتن در کارت کوچک ناقص نکن؛ ابتدا اهمیت متن را حفظ کن، بعد Layout را اصلاح کن.
- اگر Design فقط با متن مبهم یا بیش از حد کوتاه کار می‌کند، Design باید تغییر کند.

## همکاری با UX Writing

وقتی `ux-writing` هم فعال است:

- `ux-writing` را برای الگوهای فرم، خطا، دسترس‌پذیری و Microcopy استفاده کن.
- این Skill را برای فارسی طبیعی، حذف ترجمه تحت‌اللفظی، تست کلاس پنجم و ساده‌سازی مفهوم استفاده کن.
- نتیجه نهایی باید هم از نظر کاربرد UI درست باشد، هم مثل فارسی واقعی شنیده شود.

## همکاری با RTL Audit

هنگام استفاده با `i18n-rtl-audit`:

- متن را از نظر جهت، ترتیب فارسی/انگلیسی، نیم‌فاصله و شکستن خط بررسی کن.
- `dir="rtl"` یا `lang="fa"` را فقط در صورت نیاز فنی و مطابق ساختار پروژه تغییر بده.
- نام فایل، URL، شناسه، Event و کد را ترجمه یا RTL نکن.
- نسخه موبایل را با متن واقعی فارسی تست کن؛ Lorem Ipsum یا متن کوتاه ساختگی جایگزین مناسبی نیست.

## همکاری با QA

قبل از انتشار Copy مرتبط با CTA، Form یا Navigation:

- مقصد لینک را Verify کن.
- متن دکمه با نتیجه واقعی مقصد هماهنگ باشد.
- خطاها، حالت Loading و موفقیت را بررسی کن.
- هیچ Copy نباید 404، Feature ناقص یا مسیر قدیمی را معتبر جلوه دهد.

با `broken-link-scan`، `form-validation-scan` و `diff-risk-review` نتیجه را بررسی کن، اما اجازه نده Skill تشخیصی بدون Scope مشخص کد را بازنویسی کند.

## کار داخل Repo

### قبل از تغییر

- `README` و فایل شروع پروژه را بخوان.
- Current State، Next Steps، Known Issues و Open Decisions را بررسی کن.
- Branch و `git status` را ببین.
- فایل Copy، Route و Backend مرتبط را مشخص کن.

### هنگام تغییر

- فقط فایل‌ها و Stringهای داخل Scope را تغییر بده.
- ID، class، data attribute، form key، analytics event، route و API contract را حفظ کن مگر Task صریحاً تغییرشان دهد.
- تغییر Copy را از Refactor، Analytics یا Redesign جدا نگه دار.
- متن Feature نساخته را وارد صفحه نکن.

### بعد از تغییر

- Diff را برای حذف تصادفی متن، Tag یا Attribute بررسی کن.
- صفحات 360، 375، 390 و 430 پیکسل را برای متن‌های اصلی تست کن.
- RTL و ترکیب فارسی/انگلیسی را بررسی کن.
- CTAها و فرم‌های درگیر را تست کن.
- تغییرات را در Documentation پروژه ثبت کن اگر قانون Continuity پروژه چنین چیزی می‌خواهد.

## تشخیص سطح تغییر

### Copy-only

فقط Stringهای visible تغییر می‌کنند. رفتار، Layout، route، field و backend ثابت می‌مانند.

### Copy + presentation

برای خوانایی، line break، عرض متن، spacing یا hierarchy کوچک تغییر می‌کند. این تغییر را صریح گزارش کن.

### Behavior-affecting

تغییر متن به route، فرم، state، شرط، analytics یا backend نیاز دارد. بدون مجوز صریح وارد این سطح نشو.

## Conflictهای رایج

### Copy ساده با دقت حقوقی تعارض دارد

اصطلاح دقیق را نگه دار و زیرش توضیح ساده بده. متن قانونی را جایگزین یک خلاصه ناقص نکن.

### برند لحن گفتاری می‌خواهد ولی Surface حساس است

گرما را حفظ کن، اما شوخی، اغراق و اطمینان بی‌جا را حذف کن.

### متن کوتاه روی موبایل جا نمی‌شود

اول Layout و hierarchy را بررسی کن. معنی را قربانی عرض کارت نکن.

### کاربر اصطلاح تخصصی را می‌شناسد

اصطلاح را نگه دار و از توضیح اضافه بی‌فایده خودداری کن.

## گزارش Conflict

وقتی نیاز به تصمیم وجود دارد، کوتاه و شفاف گزارش کن:

```text
CONFLICT:
[دو قانون یا واقعیت متعارض]

WHY IT MATTERS:
[اثر روی فهم، حقیقت یا اجرا]

SAFE OPTIONS:
A. ...
B. ...

RECOMMENDATION:
[پیشنهاد با دلیل]
```

وقتی Conflict واقعی وجود ندارد، سؤال اضافه نپرس و کار را کامل کن.
